# SPEC – langxyne

The consumer-facing contract of the API generator: what a definition may say, and what every compliant implementation produces from it. How this implementation does so is in ARCHITECTURE.md beside this file. Where the generator sits in the build is in the root ARCHITECTURE.md, "API generation".

## Purpose

A userspace API is stated once, in a definition file, and every artifact a consumer needs is generated from it: a C header that also carries, for the implementation's build only, the wrapped API's header and a compile-time check that the constants pinned to it agree; a header-only C++ wrapper; a LuaJIT module; a Rust binding; a Rust ABI relay, which exports the C ABI from a Rust implementation; implementation stubs in C++ and Rust; a Go binding over cgo; a Python module over ctypes; and, for the library built as a WASI module, a Rust wasm shim beside the relay and a Node binding, an ES module with its TypeScript declarations. The definition is the source of truth; the artifacts are build products and are never edited. The definition states meaning, not shape: each output is idiomatic for its own language, and no output copies another's form. The implementation is a library, which the Lua module loads by name, the Python module and the Node binding from a fixed path, and the Rust and Go bindings link, by the name `_general._bound_library` gives (see "The library").

## The library

The definition names the library, never its file: `_general._bound_library = "xy"`, or `--library xy`. Each output that loads or links it renders that name, and the platform's loader or linker derives the file from it, so no output spells a file name and the same definition and flags generate the same text on every host. A library is linked one of two ways, `--link=shared` (the default) or `--link=static` (see "Invocation"). Its file, for the name `xy`:

| platform | shared | static |
|---|---|---|
| Linux | `libxy.so` | `libxy.a` |
| macOS | `libxy.dylib` | `libxy.a` |
| Windows | `xy.dll` | `libxy.a` |
| WASI | `xy.wasm` | — |

The WASI row is the library built as a WASI module, the one file an output writes the name of, as the Python module writes its table: the Node binding loads it from beside its own file, or from the absolute path its caller passes; a relative path raises, and nothing is searched. A WASI module is never linked statically. The module is a WASI reactor: it exports no `_start`, exports `_initialize` where it has constructors to run, and exports `memory`, the relay's functions and the shim's; a Rust `cdylib` for `wasm32-wasip1` links wasi-libc's `crt1-reactor.o` to be one.

The Python module loads the file of its platform from its own directory, or from the absolute path the environment variable `NS_LIBRARY` names (`XY_LIBRARY`); a relative value, or a file that does not load, raises `ImportError`. It never searches, so no file in the working directory or on a search path is loaded in its place.

Windows is the GNU toolchain's (`x86_64-pc-windows-gnu`), the one cgo links with.

## The definition

One TOML file whose name ends in `.adef.toml`, the rest of it free: the outputs take their names from `_general._name`, never from the file's.

The admissible shape of this format — keys, types, required properties, the one spelling of each `_` key — is declared in `api_def.schema.json`, a JSON Schema draft 2020-12 checked at load where `jsonschema` is installed (see "Invocation"); its version is the `vN` in its `$id`, bumped when admissible shape changes.

Every key that is not a name begins with `_`, at every level: every other key is a member name (a constant, field or parameter), and no member name begins with `_`. `[_general]` describes no item, so every one of its keys is a `_`-prefixed property too. `[_wrapped_api]` describes no item either: it holds the properties `_headers` and `_pinned_value`, and the members of `_pinned_value` are names.

- Group and item properties: `_docstring` (documents the group or item it is on), `_return` (functions and callback types only), `_base_type` (enums, constant groups and boxed scalars only), `_to_string` (enums, bit and plain constant groups only), on an opaque ref `_class`, `_ctor`, `_dtor`, `_hides_pointer`, on a union `_mixed_type_list`, and `_stack_mb` (functions only).
- Entry attributes: on a constant `_value`, `_docstring`, and for an integer `_format`; on a struct field `_type` and `_docstring`; on a union's member `_tag`, `_type` and `_docstring`; on a parameter `_type`, `_ref`, `_count`, `_optional`, `_wrote_needed`, `_docstring`; on a callback type's parameter `_type`, `_ref`, `_count`, `_docstring`, any other key being unknown there (`callback.on_batch.seen: unknown key(s) _optional`).
- A naked value is sugar: a constant `name = 4` (or `name = ["a", "b"]`) is exactly `name = { _value = 4 }`, and a field or parameter `name = "u32"` is exactly `name = { _type = "u32" }`. An inline table and a nested `[a.b.c]` table are the same thing; both are accepted everywhere.
- `_ref` states how the callee reaches a parameter: `"in"` is read by the callee, `"out"` is written by it, `"inout"` is both; absent means by value. A buffer requires `_ref` (`function.send.buf: a buffer needs _ref`).
- `_count` is one of the unsigned integer types `"u8"`, `"u16"`, `"u32"`, `"u64"`, and makes the parameter a **buffer**: the type of its count. It is required on a `memory` parameter, a buffer of bytes counted in bytes (`function.send.buf: a 'memory' parameter requires _count, one of u8, u16, u32, u64`). On a parameter of a union type that declares `_mixed_type_list = true` it makes the parameter a **list** of that union's members, variable in size: the pointer `p`, its count in members `p_count`, and its byte extent `p_bytes`, each count of the `_count` type; every counted parameter of one union, a function's or a callback's, has one `_count` type, a second refused naming the first (`function.g.q: union 'note' is counted by u16 here and by u32 at function.f.p; one count type per union`); on a union without the property it is refused, naming the parameter, the union and the property (`function.f.p: a counted parameter needs union 'note' to declare _mixed_type_list = true`). A union parameter is `in` only, a function's parameter or a callback's view, and may be `_optional` as an `in` buffer may; one with `_ref = "in"` and no `_count` is refused (`function.f.p: a union is passed as a list; it needs _ref = "in" and _count`), and `out`, `inout`, a union as a struct field and a union by value as not implemented, naming the parameter or field (`function.f.p: a union with _ref = "out" is not implemented, only "in"`, `struct.s.f: a field of union 'note' is not implemented`, `function.f.p: union 'note' by value is not implemented`, `callback.c.p: union 'note' by value is not implemented in a callback`). On a parameter of any other type it makes the parameter a **typed array** of that type, its element, counted in elements: `items = { _type = "entry", _ref = "out", _count = "u64" }`, `cuts = { _type = "cut", _ref = "in", _count = "u32" }`. An array is `in` or `out`, its element a builtin scalar, a boxed scalar or a struct, or, for a function's own `in` array, whose values the caller made, an enum. An `inout` array, an array of an opaque ref or a callback type, and an array of an enum the library writes, an `out` array or a callback's view, which a binding would have to check element by element, are refused as not implemented (`function.f.p: an array with _ref = "inout" is not implemented, only "in" or "out"`, `function.f.p: an array of typed_const 'status' is not implemented`, `function.f.p: an array of opaque_ref 'token' is not implemented`).
- `_optional = true` marks an `in`, `out` or `inout` struct, boxed scalar or scalar parameter, or a buffer with `_ref = "in"`, as one whose null the caller may pass instead of a value; refused everywhere else, naming the parameter: on a parameter with no `_ref` (a by-value parameter has no null to pass) and on a buffer with `_ref = "out"` or `"inout"` (`function.recv.pdst._optional: a buffer is optional only with _ref = "in"`). A constructor's cached `out` parameter (see the C++ wrapper and the Lua module below) ignores it, since the binding always supplies that parameter itself.
- `_wrote_needed = true` on an `out` buffer, `memory` or an array, says the callee reports, each in its count's type and units, how much it wrote, a prefix of the buffer, and how much the whole result needs. A buffer too short for the whole result is not a failure: the call returns the zero-valued entry, having written what fits, and the reports say what the caller's retry needs, so every binding hands both reports to its caller after a successful call and reads them at no other time. Refused on any other parameter, naming it (`function.send.buf._wrote_needed: only an "out" buffer reports what it wrote and needs`), and as anything but a boolean (`function.list.items._wrote_needed must be true or false`).
- `_stack_mb = "<entry>"` on a function names an `untyped_const` entry, a positive integer: the stack, in MiB, a call of the function needs on the caller's thread where the library runs it there, as a WASI module does; an entry of no `untyped_const` group, or one not positive, is refused naming the function (`function.run._stack_mb: 'big' is not an untyped_const entry`). The Node binding checks it; every other output ignores it.
- `_format` is `"hex"` or `"dec"` (the default): how the number is spelled where a literal is emitted.
- `_to_string = "<name>"` asks for a function converting a value of the group to text, named `<name>` as each output's section below states; absent, no conversion is generated for the group. `<name>` is a name like any other: the identifier and keyword rules below apply to it. An enum converts a value to its entry's unprefixed name (`"ERR_TIMEDOUT"`), and a value no entry has to `UNKNOWN_<ENUM>` (`UNKNOWN_RESULT`). A plain group does the same, converting to the later entry where two share a value, with `UNKNOWN` for a value no entry has. A bit group decomposes the value: each entry with exactly one bit set, in document order, whose bit is present contributes its unprefixed name and removes its bit; the names are joined with `|`, and any bits left over follow as one final term, `0x` and their lower-case hex without padding; zero converts to `NONE`. A composed entry with more than one bit is never matched: with entries `a` bit 0, `b` bit 1 and `ab = ["a", "b"]`, 3 converts to `A|B`, 1 to `A`, 0 to `NONE` and 9 to `A|0x8`.

Every kind below but `[_general]` and `[_wrapped_api]` is an array of groups, `[[kind]]`: each group is a table whose `_`-prefixed keys are its properties and whose other keys are its members, and has at least one member, else it is refused as `<kind>[<i>]: has no entries`, `<i>` the group's index from 0. A constant kind's (`untyped_bit_const`, `untyped_const`, `string_const`) members are its constants. A named kind's (`typed_const`, `opaque_ref`, `boxed_scalar`, `struct`, `union`, `callback`, `function`) members are its items, each `<name> = <table>`, the table the item's body, so a `[function.open]` written after a `[[function]]` header is the item `open` of that group; such a group's one property is an optional `_docstring`. An item body that is not a table is refused as `function.open must be a table`. An item's name is unique within its kind across every group: a repeat is refused against the later one, which is dropped, as `function.open: already defined in function[0]`, naming the first one's group. An objection names an item by kind and name whichever group holds it (`function.open`, `struct.stats.count`), and a group by its index (`function[1]: has no entries`, `function[1]._docstring must not contain a line break`, `function[1]: unknown key(s) _colour`). A group's docstring describes no item: each output renders it as a comment, where its section below states. A named kind's item written with no group, `[function.open]` with no `[[function]]` before it, makes `function` a single table, which is refused as `[function] must be an array of tables, [[function]]`.

The file holds these tables, each optional unless stated; any other top-level table is an error:

- `[_general]` (required): `_name` (an identifier, required; names every output, as `<name>` in each output's path below), `_namespace` (an identifier, required; the prefix for everything generated), `_version` (four integers 0..255, required, encoded most-significant first into one 32-bit value), `_bound_library` (the library's name, which the Lua and Python modules load and the Rust and Go bindings link, see "The library": ASCII letters, digits, `_` and `-`, not beginning with `-` or `lib` (LuaJIT does not prefix such a name again while a linker does), else `_general._bound_library: 'x.y' is not a library name: ASCII letters, digits, '_' and '-', not beginning with '-'`; a value with the form of one of that table's files is refused naming the name it holds, `_general._bound_library: 'libxy.so' is a file name; name the library 'xy'`, and a name beginning with `lib` naming the rest where that is a name, `_general._bound_library: 'libxy' begins with 'lib', which LuaJIT's loader does not add again and a linker does; name the library 'xy'`).
- `[[untyped_bit_const]]`: an array of groups of constants that are bit flags. Each group has an optional `_docstring`, an optional `_base_type`, an optional `_to_string`, and at least one entry. An integer value is a bit index whose flag is a positive value of the group's base type: 0..30 under `i32`, 0..31 under `u32`. A list sums its terms into the entry's value: each term is an earlier entry of this group or of an earlier group of the same base type, or a literal integer fitting the base type, written as a string in decimal or in hex with a lower-case `0x` prefix, either with an optional leading `-` and nothing else (`"4"`, `"-4"`, `"0x1f"`); any other term that is not an entry name is refused; the loader refuses a term naming an entry of another base type, naming both entries and both base types, and a sum whose terms share a bit, naming the two.
- `[[untyped_const]]`: an array of groups of plain integer constants, with the same group properties. A value is an integer fitting the group's base type (`i32`: -2^31..2^31-1; `u32`: 0..2^32-1), or a list summing the same kind of terms `untyped_bit_const` composes — an earlier entry of this group or of an earlier group of the same base type, or a literal integer fitting the base type — with that range applied to the sum; a term naming an entry of another base type is refused the same way. A floating-point value, or a `_base_type` of `f32` or `f64`, is refused as not implemented.
- `[[string_const]]`: an array of groups of string constants, each with an optional `_docstring` (no `_base_type`: a string has no fixed-width representation; no `_to_string`) and at least one entry. Values are strings containing no `"`, `\` or control character (U+0000..U+001F, U+007F).
- `[[typed_const]]`: an array of groups of enumerations, each item `<enum>` with an optional `_docstring`, `_base_type` and `_to_string`. Values are integers fitting the enum's base type.
- `[[opaque_ref]]`: an array of groups of handle types, each item `<name>` a handle type whose representation is the implementation's secret. It has no members, only properties: `_docstring`; and for bindings with object semantics, `_ctor`, the function that produces the handle (it has exactly one parameter of this type with `_ref = "out"`), `_dtor`, the function that releases it (its only parameter is this type by value; requires `_ctor`), and `_class`, the object's name in those bindings, written idiom-free (lowercase identifier; default the ref's name). Each binding applies its own casing. `_hides_pointer = true` (a boolean, default false, else `opaque_ref.port._hides_pointer must be true or false`) says the handle is a raw pointer the library does not validate, so a dynamic-language binding wraps the lifetime of an object with a `_dtor` itself (see "Objects and concurrency").
- `[[boxed_scalar]]`: an array of groups of boxed scalars, each item `<name>` a distinct kind of integer, so that two quantities of the same width, a device offset and a byte count, cannot be passed one for the other. It has no members, only properties: `_docstring` and `_base_type` (required). A boxed scalar is a parameter type, by value or with any `_ref`, `_optional` as for a scalar, an array's element, and a struct field type; it is not a `_return` type.
- `[[struct]]`: an array of groups of structs, each item `<name>` an optional `_docstring`, then fields in document order.
- `[[union]]`: an array of groups of tagged unions, each item `<name>` an optional `_docstring`, an optional `_mixed_type_list` (a boolean, default false, else `union.note._mixed_type_list must be true or false`), which states that the members lie in a list back to back, each by its own size, and alone admits a counted parameter of the union, a list (see `_count`), then members in document order, each `<member> = { _tag = "<constant>", _type = "<struct>" }` with an optional `_docstring`, no naked value standing for it: `_tag` an `untyped_const` entry, `_type` a struct. Every member struct begins with one and the same struct, the union's prefix, whose first field is the tag, `u8`, `u16` or `u32`, and whose first field after the tag that is not `u8` is the record's own byte length, `u16` or `u32`, so any fields between the two are `u8`; the prefix is the type of every member struct's first field, read one level deep. This shape holds of every union, `_mixed_type_list` or not. The tag's value fits the tag field; each member struct has the prefix's alignment, which is so the list's alignment, the largest of any field in any member, its fields ending at a whole multiple of it, no padding, itself or in a struct it holds, no opaque ref, whose size is each target's, and a size the length field holds; the prefix's fields end at a whole multiple of the list's alignment and it has no padding either; no two members share a tag's value or a struct. Each refusal names the union, and the member where one breaks the rule: `union.note: names no member`, `union.note.line: a member needs _tag and _type`, `union.note.line._tag: 'go' is not an untyped_const entry`, `union.note.line._type: struct 'note_nope' must be defined before it is used`, `union.note.line._type: 'flow' is not a struct`, `union.note: members must begin with one struct; line begins with 'note_alt' and mark with 'note_head'`, `union.note.line._type: struct 'note_line' must begin with a struct field`, `union.note: prefix 'note_head' must begin with the tag, u8, u16 or u32, then any u8 fields, then the record's byte length, u16 or u32`, `union.note.line._tag: kind_line's value 70000 does not fit note_head.kind (u16)`, `union.note.mark._tag: kind_line is already union.note.line's tag`, `union.note.mark._type: struct 'note_line' is already union.note.line's struct`, `union.note.mark: struct 'note_mark' has alignment 8 (field 'value' is i64); a member of 'note' has the prefix's alignment, 4`, `union.note.mark: struct 'note_mark' is 46 bytes, not a multiple of the list's alignment, 4`, `union.note: prefix 'note_head' is 5 bytes, not a multiple of the list's alignment, 2`, `union.note.mark: struct 'note_mark' has padding after field 'value'; a member has none`, `union.note.line: struct 'note_line' of 65544 bytes does not fit note_head.size (u16)`. A struct's and a union's layout is C's on every target the outputs build for: a builtin scalar is as wide and as aligned as its width, the text type two `u32`, an enum or boxed scalar its base type, and a struct its fields in order each at the next offset its alignment allows, its alignment the largest of theirs and its size rounded up to it. For a union declaring `_mixed_type_list`, every output that renders its list publishes the list's alignment as one named constant, the unit of the index each binding's `at` takes, so no consumer computes it; each output's section below names its form.
- `[[callback]]`: an array of groups of callback types, each item `<name>` a function type the library calls (see "Callbacks"): `_return` (required), an optional `_docstring`, then parameters in document order. `_return` names a `typed_const` with a zero-valued entry, which continues, and a non-zero one, the first of which in document order stops (`callback.on_batch._return: typed_const 'flow' has no non-zero entry to stop with`). A parameter is by value a builtin scalar or an enum, or, with `_ref = "in"` and `_count`, a **view**, a buffer of bytes (`memory`), an array of a builtin scalar, boxed scalar or struct, or a list of a union's members, which the library passes read-only for that call of the callback only; it expands as a function's buffer does. Anything else is refused as not implemented, naming it: a boxed scalar or struct by value (`callback.on_batch.seen: a struct 'stats' by value is not implemented in a callback`), an opaque ref, a non-buffer `_ref` and any `out` or `inout` (`callback.on_batch.seen: a callback parameter with _ref = "out" is not implemented, only a buffer with _ref = "in"`), an enum view, `text`, and a callback type (`callback.on_batch.seen: callback 'on_batch' as a callback's parameter is not implemented`). The C callback type's own last parameter is `user_data`, so a parameter named `user_data` is refused (`callback.on_batch.user_data: 'user_data' is the C callback type's own last parameter`).
- `[[function]]`: an array of groups of functions, each item `<name>`: `_return` (a `typed_const` enum name whose entries include the value 0, required), an optional `_docstring`, then parameters in document order. A buffer `p` becomes, in the C header and every output that mirrors it, adjacent parameters: the pointer `p`, then its count `p_count` of the `_count` type, then with `_wrote_needed` the pointers `p_wrote` and `p_needed` to that type, through which the callee reports. A parameter `p` of a callback type, by value, becomes the callback type's pointer `p`, then `void* p_user_data`, which the library passes back as the callback's `user_data`; a `_ref` on it is refused (`function.stream.sink: a callback is passed by value`). The definition does not write the count, the reports or `p_user_data`; a numeric parameter written beside a buffer is just another parameter.
- `[_wrapped_api]`: the wrapped API: its C headers, which the implementation includes, and the constants of this API pinned to those headers' macros. `_headers` (required) is a non-empty list of the wrapped API's header paths, each relative to the project directory, else `_wrapped_api._headers must be a non-empty list of strings`; each element is refused, naming it by its index, `_wrapped_api._headers[1]`, if it holds a quote, backslash or control character, if it is absolute or begins with `../`, and if an earlier element is the same path (`_wrapped_api._headers[1]: already listed`). `_pinned_value` is a table whose each member maps an `untyped_bit_const` key to the macro of those headers it must equal. Absent `[_wrapped_api]`, no output refers to a wrapped API; present without `_pinned_value`, or with it empty, the headers are still included and nothing is pinned.

`_base_type` is `"i32"` (the default) or `"u32"`, and chooses the fixed-width type of an enum or a group's constants: the C header types a group's constants by it, the C++ wrapper takes that type from the header, and the wrapper's enum classes and the Lua FFI declarations name it. On a boxed scalar it is the type of the one value the box holds, required and wider: any integer type, `i8` through `u64`; a floating-point type, `memory` or a definition's own type is refused.

Rules a definition must satisfy:

- Types are the integer types `i8`, `u8`, `i16`, `u16`, `i32`, `u32`, `i64`, `u64`, the floating-point types `f32`, `f64`, `memory`, `text`, or a name from `typed_const`, `opaque_ref`, `boxed_scalar`, `struct`, `union` or `callback`. A union is a parameter type only, as a list (see `_count`). A callback type is a function's by-value parameter type only: as a struct field (`struct.hook.cb: a field of callback 'on_batch' is not implemented`), an array's element, a callback type's parameter, and a constructor's parameter (`opaque_ref.port._ctor: function.open_port.sink: a constructor's callback parameter is not implemented`), since an object would hold it past the call, it is refused as not implemented. The builtins other than `memory` and `text` are variable types only: `_base_type` and `_count` take the values stated for them. `text` is a struct field type only: a run of bytes in a byte arena, as its offset and its length, each `u32`, no encoding assumed. No definition states which arena a text field indexes; whoever reads one names the arena, typically a `memory` `out` buffer with `_wrote_needed` of the same call. A `text` parameter, an array of `text` included, is refused as not implemented (`function.f.p: a text parameter is not implemented; text is a struct field type`). Those six categories share one namespace; a name in two of them is an error (`struct.note: type name already defined in union`), as is shadowing a builtin (`struct.text: shadows builtin type text`).
- A key beginning with `_` that is not recognised where it appears is an error naming the key and where; so is a key not beginning with `_` inside an entry's table or an opaque ref. A kind other than `[_general]` and `[_wrapped_api]` written as a single table is an error: each is an array of tables, `[[...]]`. A group has at least one entry.
- None of a buffer's `p_count`, `p_wrote` and `p_needed`, a list's `p_count` and `p_bytes`, nor a callback parameter's `p_user_data`, is the name of another parameter of the same function or callback type (`function.list.items: its report parameter items_wrote is already a parameter`, `function.replay.notes: its extent parameter notes_bytes is already a parameter`, `function.stream.sink: its user_data parameter sink_user_data is already a parameter`).
- Every name is a C identifier that is neither a C, C++, Lua nor Rust keyword. No parameter is named like a name a binding's generated code itself uses where that parameter is in scope; each binding's section below says so.
- A composed constant names only entries defined before it, in its own group or an earlier one of the same `_base_type`. Its sum's running total, term by term in the order written, fits the base type at every step, not only at the end, naming the term after which it does not: a constant expression that overflows midway is a compile error in Rust and undefined in C. A pin names an existing `untyped_bit_const` entry. Constant names are unique across every constant group, the string constants, every enum, and the version constant; the C identifiers of enums, opaque refs and their tags, boxed scalars, structs, callback types, functions and, where some struct field is `text`, the text type `ns_text` are unique together (`function.text: C identifier xy_text already defined by the builtin type text`).
- Within one enum, no two entries share a value.
- Docstrings contain neither `*/`, `]]` nor a line break: the bindings, the Rust relay and the Rust stub render a docstring as a line comment, which a line break would end.
- Order is meaning: parameters, fields, groups and the items of a group appear in every output in the order written.
- A ctor has no buffer with `_ref = "out"` and no parameter with `_ref = "inout"`: the bindings cache every other `out` of the ctor on the object, a buffer has no owner there, and a constructor has nothing to return an updated value through.

## Callbacks

A callback is a parameter of the call that drives it, borrowed for that call only. The library calls it only during that call and only on that call's thread, and keeps neither it nor its `user_data` after returning; every view it passes is read-only and valid for that call of the callback only. The definition can express nothing else (see the `[[callback]]` and type rules above). `user_data` is the C ABI's: each binding passes its own state for the call through it, and a C caller passes whatever it likes, which the library hands back unchanged on every call. A callback does not call into the library on the object whose call drives it, and each binding refuses such a call before it reaches the library (see its section; a raw call, `M.raw` or the `ffi` functions, is not checked). The library does not invoke a callback while an earlier invocation of it has not returned. Until a callback returns, the library writes, moves and frees none of the memory its views cover, and it treats every answer other than the zero entry as stop. A callback returns normally: a C caller's callback neither unwinds nor `longjmp`s across the library's frames.

In each binding the consumer's code answers the return enum, its zero entry continuing: the Rust binding's closure returns the enum, the C++ wrapper's callable the enum class, the Go binding's func the enum, the Lua module's function `nil`, the zero entry, or a number, the Python module's callable `None`, the zero entry, a member of the return enum, or an `int` the return enum's base type holds, never a `bool` or another enum's member, anything else being a failure, and the Node binding's function `undefined` or an integer the return enum's base type holds, anything else being a failure. The library's answer to a stop is the driving call's result, returned as any result is. Where the consumer's code fails inside the callback, a Rust or Go panic, a Lua or Python error (any `BaseException`) or anything a JavaScript function throws, the binding answers the stop entry, the first non-zero entry in document order, never calls the consumer's code again during that driving call, through any of the call's callbacks, and raises the first failure only, lets nothing unwind through the library's frames, and raises the failure again once the driving call returns, before it examines the result. A nested invocation, the library calling a callback while an earlier invocation of it runs, reaches no consumer code: the binding answers the stop entry and, but in the C++ wrapper, which answers stop to every later invocation and returns the library's result, records it as the call's failure. A C++ callable that throws terminates the process, the trampoline being `noexcept`. A signal arriving while the library runs can raise in the Python trampoline before its first statement, which no Python code encloses: ctypes reports it and the library receives an undefined answer.

The bindings check what the library hands a callback:

- The calling thread: the Rust binding's and the C++ wrapper's trampoline compare it with the driving call's, and on a mismatch abort the process, the message naming the C callback type and the C function (`xy_on_batch called on another thread than the one calling xy_stream`). The Python module compares it the same way and on a mismatch fails the call through the failure path above, a `RuntimeError` of that message, never reaching the callable: the interpreter stays sound on any thread. The Go binding checks nothing, its callback type's doc comment stating the rule: the Go runtime runs a call from another thread soundly, and a thread identity is stable only under `runtime.LockOSThread`. The Lua module checks nothing: LuaJIT's VM is single-threaded, and a call from another thread corrupts it before any check could run. The Node binding checks nothing: an instance belongs to the one JavaScript agent that loaded it, and the library runs on that agent's thread.
- Each view is the library's, a union's list allocated at the list's alignment and typed to carry it, a pointer to its prefix (see the C header); the C++ wrapper and the Lua module check no view. In the Rust binding: null with a count of 0 is an empty slice; null with any other count, a misaligned pointer, or a count whose bytes exceed `isize::MAX` panics through the failure path above, the message naming the C callback type and the view. In the Go binding null with a count of 0 is a nil slice, and null with any other count, or a count Go's slices cannot hold, panics through the failure path with `unsafe.Slice`'s own message; a union's list null with a count or an extent but 0, or not aligned to the prefix, panics through the failure path naming the C callback type and the view. In the Python module null with any count but 0 is a `RuntimeError` through the failure path, naming the C callback type and the view (`xy_on_batch received view fresh outside the definition`), and in the Node binding an `Error` of the same message, a union's list null with a count or an extent but 0 alike.
- The Node binding's `user_data` is the id of a frame its driving call made, never 0; one naming no frame of that callback type in progress answers the stop entry before any consumer code runs.
- An enum by value, in the Rust and Go bindings, the Python module and the Node binding: a value no entry names fails the same way, naming the C callback type and the parameter.
- A thread mismatch, a throw from a C++ callable and a Rust abort end the host process, as does a Go func ending its goroutine (`runtime.Goexit`, which `testing`'s `FailNow` calls), since that unwinds through the library's frames, and the Lua module detects no foreign thread, whose call corrupts the VM: a host isolates the library accordingly.
- The C++ wrapper checks each call's own thread: one callable passed to calls on two threads must be safe to call concurrently.
- The bindings trust `user_data`: a library passing one callback's `user_data` beside another callback's pointer answers outside the definition, and the result is undefined.

No binding copies a view: the Rust binding hands slices, the C++ wrapper pointer and count, a union's list as its `USequence`, the Go binding slices over the library's memory, a union's list as its `USequence` over it, the Lua module cdata pointers and counts, and the Python module and the Node binding a lazy view, each resolver resolving a text against a view as against any arena. The Python module's view reads an element only when indexed, each element read a copy, a boxed scalar's its base value, a slice of a byte view `bytes`, and refuses any use once its callback returns and on any thread but its callback's with a `ValueError`; the Node binding's view is the same over the instance's current linear memory, read afresh at each access since the memory's growth detaches an earlier buffer, a slice of a byte view a `Uint8Array`, and refuses any use once its callback returns with an `Error`; in the Go binding a slice kept past its func reads memory the library may have reused, as the callback type's doc comment states. Each slice is read-only; writing one, or appending to a slice sharing its memory, is a consumer error the library cannot detect, and `Text.Resolve`'s result shares its arena's lifetime and cannot be grown into it. In the Lua module a view is unchecked: one kept past its callback, or indexed past its count, reads memory the library may have reused; `M.resolve` over a byte view takes its bound from the library's count while the callback runs.

## Objects and concurrency

A binding owes the safety its language's own concurrency model lets a program reach; a program that reaches past that model, through a raw FFI thread in LuaJIT or a raw handle in C, owns what follows. The rule governs the class of every opaque ref with a `_dtor` and `_hides_pointer = true`, and each binding's conformance to it is judged by its own language. A library that validates its own handles, answering a status for a null, destroyed, unknown or busy one rather than reaching freed memory, leaves `_hides_pointer` unset: the library then carries the safety, and what a caller sees after release is the library's own status.

- Python's threads are inside its model, so where `_hides_pointer` is set the Python module's class takes one lock per object and the object's calls are mutually exclusive: a call or a release during another call of the same object, from that call's callback or from another thread, raises the busy error; a call after release, and a second release, raise the after-destroy error without reaching the library; the finalizer destroys only an object no call holds. Where it is unset, the class has no lock, and every call after release, a second release included, reaches the library with the null handle and raises the library's status. Every class with a `_dtor`, either way, is a context manager whose `__exit__` releases and suppresses no exception. Its section states each of these.
- A JavaScript agent runs one call at a time, so the Node binding's objects meet the rule without a lock: where `_hides_pointer` is set, an object is held for each of its calls, a call or a release from that call's callback throws the busy error, and a call after release, and a second release, throw the after-destroy error without reaching the library; where it is unset, every call after release reaches the library with the null handle. Its section states each of these.
- LuaJIT's threads are separate `lua_State`s outside its model, so the Lua module keeps its re-entry refusal (see its section) and is to state that an object belongs to one `lua_State`.
- The C++ wrapper's, the Lua module's and the Go binding's conformance is open: each is checked
  when it is next generated for a library whose objects have a `_dtor`.

## Outputs

Every output starts with a banner naming the generator and its source and saying it is generated, `GENERATED by langxyne from <source>`, but the Go output's, `// Code generated by langxyne from <source>; DO NOT EDIT.`. Under the output directory: `include/<project>/` holds the headers and `lua/` the Lua module and the integer support module beside it; `go/<name>/` holds the Go package, `python/` the Python module and `node/` the Node binding and its declarations, whose banner says it is generated beside the module, `GENERATED by langxyne beside <name>.mjs`; `rust/` holds the Rust binding, relay and wasm shim, compile-time inputs a crate reaches from the directory the implementation's build names in `LANGXYNE_RUST_DIR` (or, for the binding, beside the crate root), never staged; `stub/` holds the implementation stubs, never staged.

Every Rust output is edition-agnostic: it compiles unchanged at edition 2021 and at edition 2024 with Rust 1.82 or later, spelling the forms both accept: `#[unsafe(no_mangle)]`, `unsafe extern "C"`, each unsafe operation inside an `unsafe fn` in an `unsafe { }` block of its own, and `core::convert::TryInto` by its path. It is `rustfmt`'s output under style edition 2024 and the default configuration (see "Invocation"). `Result` is spelled bare wherever a signature or a local's type names it; an enum's `TryFrom` spells `core::result::Result`. A function's doc comment is its docstring, then each parameter's docstring as `name: text`, then whatever lines the output adds, a bare `///` line separating the docstring from anything after it. A function the Rust stub renders with 8 or more parameters, and a Rust binding method or `create` whose parameters, `&self` counted, are 8 or more, carries `#[allow(clippy::too_many_arguments)]`: clippy's default lints refuse it otherwise.

### `include/<project>/<name>.h` — the C header

- For a consumer, includes only `<stdint.h>`. Its preprocessor content is: `#pragma once`, that include, the two blocks defining `NS_C_API` (`extern "C"` under C++) and `NS_API` (`NS_C_API` plus default visibility when `NS_IMPL` is defined), one `#define` per bit or plain constant and for the version, and the implementation-only blocks below. No macro is used in any declaration except `NS_API` before each function.
- One block at the end of the file under `#if defined(NS_IMPL)`, and so only in the implementation's build: one include per element of `_wrapped_api._headers`, in list order, as `"<project>/<header>"`, the project name joined to the element, then an include of `<assert.h>`, then one file-scope `static_assert(NS_KEY == MACRO, "...")` per pin, none where `_pinned_value` is absent or empty. The library failing to compile is the ABI check; a consumer never sees the wrapped API's header. Absent `[_wrapped_api]`, the block is not emitted.
- The version and every bit and plain constant are object-like macros, `#define NS_KEY <value>`, each typed by its `<stdint.h>` constant macro. The version is `UINT32_C(0x...)`, its four bytes as eight hex digits. In a group, the base type's macro (`INT32_C` for `i32`, `UINT32_C` for `u32`) wraps a literal value, spelled per `_format`, and a single bit's one: `INT32_C(16)`, `UINT32_C(0xbeef)`, `(INT32_C(1) << n)`. A negative value keeps its sign outside the macro, which wraps its magnitude, `(-INT32_C(0x5))`; the base type's minimum, whose magnitude the type cannot hold, is `(-INT32_C(0x7fffffff) - 1)`, spelled per `_format` the same way. A composed entry's sum is symbolic and parenthesised, `(NS_A | NS_B)` in a bit group and `(NS_A + NS_B)` in a plain group, a literal term rendered as a literal value is, in the base it was written in, `(NS_A | INT32_C(4))`, `(NS_A + (-INT32_C(0x3)))`. Each group is one run of macros under its docstring comment. Each typed enum is an enum with explicit values and a typedef, a non-negative value spelled per `_format` and a negative one as a negative group value is. Each string constant group is a run of `static const char NS_KEY[] = "...";`.
- Each opaque ref is an incomplete struct and a pointer typedef. Each boxed scalar is a struct of one member, `typedef struct ns_b { T value; } ns_b;` with `T` its `_base_type`'s C type, under its docstring comment, after the opaque refs and before the structs, so that a struct may hold one; C passes and returns it by value, a type distinct from every other. Where some struct field is `text`, and only there, the text type follows the boxed scalars and precedes the structs, `typedef struct ns_text { uint32_t offset; uint32_t length; } ns_text;`, and a field of type `text` is an `ns_text`. Each struct has its fields in order with a typedef. Each callback type follows the structs and precedes the functions, as the typedef of a pointer to its function type, its parameters mapped as a function's are and `void* user_data` last: `typedef ns_r (*ns_c)(const ns_entry* seen, uint64_t seen_count, ..., uint32_t last, void* user_data);`. A callback type with a view states its caller's duty: its comment ends `Its views are valid for that call only.`, a comment of that sentence alone where it has no docstring.
- Functions are declared in document order. Type mapping: an integer type `iN` → `intN_t` and `uN` → `uintN_t`, `f32` → `float`, `f64` → `double`, an enum, boxed scalar, struct or callback type by its typedef, an opaque ref by value as its typedef; a non-memory type `T` with `_ref = "in"` → `const T*`, with `"out"` or `"inout"` → `T*`, so an `in` array is `const T*` and an `out` array `T*`; `memory` → `const void*` when `"in"`, `void*` when `"out"` or `"inout"`; a union's list → `const ns_h*`, `h` the union's prefix; a buffer is followed by `p_count` of its `_count` type `CT`, then with `_wrote_needed` `CT* p_wrote, CT* p_needed`, a union's list by `CT p_count, CT p_bytes`; a callback parameter is followed by `void* p_user_data`.

A method returns `None`, its one value or a tuple of them in order: each non-buffer `out`, each `inout` as written back, and each `out` or `inout` buffer's data; an `_optional` parameter admits `None`, passed as null, an `_optional` `inout` then returning `None`. An enum is passed as a member of its enum or an `int` one has, and a value the library writes is its enum's member; a struct or text is an instance of its class, and through `_ref` is copied first and passed by reference, a boxed scalar given and returned as its base value. A scalar, enum or count outside its type is refused naming the parameter, `TypeError` for the wrong type and `ValueError` for the wrong value (`Port.seek: offset must be an int uint64_t holds`), before any allocation, an `in` array's elements each so; a float is converted by `float()`. An opaque ref with a class by value or `in` is an instance of that class, else `TypeError`, whose handle is passed. Where its class has a `_dtor` and `_hides_pointer`, its lock is taken and held as the receiver's is, the call raising busy where another call holds it (`DataLink.attach: hport is a Port while xy_stream is in progress on it` where the return enum has no non-zero entry), so an object passed as its own argument raises busy, and then `ValueError` where released (`DataLink.attach: hport is a Port used after destroy_port`); otherwise the argument's handle is passed as it stands, null after release, and the argument is refused while a call of it drives a callback, as the receiver is. Any other opaque ref, or one through `inout`, is a raw handle class the module issued for that opaque, else `TypeError`, refused with `ValueError` where null (`spend: htoken is a null TokenHandle`), an `inout` one returned as the handle passed, which the library wrote. Every lock the call takes is taken, and the state of every handle it passes, the receiver's included, checked, after every other check and conversion, so no consumer code runs between them and the call; a refusal there releases every lock the call took. A `memory` `in` buffer is a bytes-like value, `out` its count, returning the `bytes` written, and `inout` a bytes-like value returned as the `bytes` written, each counted in bytes whatever its item size; an `out` array is its count, returning the `ctypes` array uncopied; an `in` array is any sequence, copied into a `ctypes` array, a boxed scalar's elements its base values; a count the count type cannot hold raises `ValueError` naming the buffer. A present buffer, empty included, passes a non-null pointer, and only `None` for an `_optional` `in` buffer passes null. A buffer with `_wrote_needed` returns its data, then what it wrote and what it needs, after checking that the library wrote no more than the buffer holds or the result needs, else a `RuntimeError` naming the C function and the buffer. A result, or an enum the library writes or passes, that its enum does not name raises `RuntimeError` naming the C function or callback type and the enum.
- Refused, each naming what it names: a Python keyword as `_general._name`, a struct field, a function, an argument a function the module renders takes (each parameter but a non-buffer `out`, an `out` buffer's being its `p_count`), a cached `out` or a conversion, or as the UpperCamel rendering of an enum, boxed scalar, struct or class; a struct field named like a classmethod of a structure the module calls, `from_buffer_copy`, `from_address`, `from_buffer` or `from_param` (`struct.stats.from_buffer_copy: 'from_buffer_copy' is a name the generated code uses`); such an argument named like a name the function's body spells beside it, `self`, `callable`, `isinstance`, `len`, `list`, `float`, `bytes`, `memoryview`, `TypeError`, `ValueError` or `RuntimeError`, or like a name the module defines; a name defined twice at module scope (a constant, a conversion, an enum, a raw handle class, a boxed scalar, `Text` and `resolve` where generated, a struct, `Error`, a class, a function no class renders, or a builtin the module spells, such as `len` or `Exception`) or in a class (`handle`, `property`, `release` where a `_dtor` generates it, a method, a cached `out`), naming every definer; and a module-scope name a union's rendering defines, `USequence`, `U_ALIGN` or `UnionError`, that anything else defines, naming the union (`struct.note_sequence: module scope name NoteSequence already defined by union 'note'`).

### `node/<name>.mjs` — the Node binding, and `node/<name>.d.mts`

An ES module Node runs as written, over the library built as a WASI module beside the relay and the wasm shim, importing nothing but `node:fs`, `node:path`, `node:url` and `node:worker_threads`; its companion `node/<name>.d.mts` declares it for TypeScript, its first line after the banner `/// <reference lib="esnext.disposable" />`, so it type-checks under TypeScript's default libraries. It renders every construct the Python module renders, in JavaScript's idiom, and its doc comment, in both files, states where it departs from the Python module: no finalizer, no thread check, the dead instance and the preopens, each below.

- `load(wasi, path)` reads the module file, `<_bound_library>.wasm` (see "The library") beside the module's own file or at the absolute `path` given, a relative one a `TypeError`; instantiates it synchronously with `wasi.getImportObject()`'s imports and its own `ns__callbacks`; calls `wasi.initialize(instance)` once; and returns the library, a frozen object of every class and every function no class renders over that instance. `wasi` is a `node:wasi` WASI of version preview1 not yet started, one per `load`, since `wasi.initialize` refuses a second start, which the declarations type structurally as `Wasi`, so a consumer passes its preopens; the module reaches files through them alone, and a path the library takes is a guest path, the host's path only where the host's root is preopened at the guest's, `preopens: { "/": "/" }`, which the doc comment states. The library object holds no instance; a consumer reaching one through the binding's internal fields reaches the raw exports and owns what follows.
- Every constant is an exported `const` under its unprefixed name, as the Python module's, enum entries included, each declared as its literal type; a conversion is an exported function under the Python module's name; an enum is a frozen object of its entries, `E.KEY`, and a type of their values; a boxed scalar is its base value, its type `number`; the text type `Text` and each struct `S` a class whose constructor takes any of its fields, each other zero; each opaque ref `h` a raw handle class `HHandle`, which only an instance makes, `value` its handle's number or null. Where some struct field is `text`, `resolve(text, arena)` is the bytes of `arena` the run covers, a copy of the run alone, null where the run leaves it, `arena` bytes or a byte view while its callback runs. A result other than the zero entry throws `ResultError`, its `result` the entry's value and its message the entry's name.
- Each call, in order: refuses every argument, before anything is allocated, unless it has its parameter's type and fits it, a `TypeError` for the wrong type and a `RangeError` for the wrong value naming the parameter (`Port.seek: offset must be an integer uint32_t holds`), and copies it at that check, a `memory` argument's bytes and an array's elements included, so nothing consumer code does afterwards changes what the call writes or the count it passes; refuses an `out` buffer whose bytes would pass 2³¹−1 with a `RangeError` naming it; refuses an object or handle argument's state; allocates through `ns__alloc` in linear memory and writes the `in` values; calls; reads the `out` values and reports; and releases every block through `ns__free` on every path, every access through the instance's current `memory.buffer`. A `u32` read back from a wasm `i32` is made unsigned. Marshalling is the Python module's otherwise: a method returns `undefined`, its one value or an array of them in order; an `_optional` parameter admits `null` or `undefined`, passed as null; a `memory` `in` or `inout` buffer is an `ArrayBuffer` or a view of one, counted in bytes, `inout` returning a `Uint8Array` of what was written; an `out` buffer is its count, returning a `Uint8Array` or an array of its elements, copied; an `in` array any iterable; a buffer with `_wrote_needed` returns its data, then what it wrote and what it needs, an over-report an `Error` naming the C function and the buffer; an enum, result or value the library writes or passes that its enum does not name an `Error` naming the C function or callback type and the enum. A struct by value passes as wasm32's C ABI does, its one scalar where it holds one, else a pointer to a copy.
- A class, `C` with the constructor `new C(...)`, per opaque ref with a `_ctor`, as the Python module's: `handle` its raw handle, a getter per cached `out`, a method per member function. A class with a `_dtor` has `release()` and `[Symbol.dispose]`, which releases, so `using` releases the object at its block's end, and no finalizer: an object never released keeps its handle until its instance is gone; one whose cached `out`s a check refuses is released before the constructor throws. Where `_hides_pointer` is set, an object is held for each of its calls, and while held a call or a release of it throws the busy error, `ResultError` of the first non-zero entry of its return enum, or where that enum has none an `Error` naming the class, the method and the C function in progress; a call after release, and a second release, throw `Error` naming the `_dtor` (`Port used after destroy_port`) without reaching the library, and `handle` reads null. Otherwise every call after release, a second release included, reaches the library with the null handle, and a class whose method takes a callback refuses every call and release during such a call the same way. An object argument of another class is refused as the receiver is, naming the argument (`DataLink.attach: hport is a Port used after destroy_port`); a raw handle argument is one this instance issued for that opaque, refused where null (`spend: htoken is a null TokenHandle`).
- A function with `_stack_mb` refuses a call, before anything is allocated, on a worker thread whose `resourceLimits.stackSizeMb` is below the entry's value, with a `RangeError` naming the function and both sizes; on the main thread, whose stack Node does not expose, it checks nothing, and its doc comment states the need.
- A callback parameter is a function, refused with a `TypeError` naming the parameter otherwise. For each call the binding makes a frame of it, whose id, never 0, is the `user_data`, and passes the address `ns__address_c` answers; the instance's `ns__call_c` import calls the function by the frame its `user_data` names, every statement under one `try`, so nothing the function throws leaves it into the module; once the instance is dead, found on entry or after the function returns or throws, it throws the dead-instance error into the module instead of answering, so no code of a dead instance runs again; it builds each view and enum and answers as "Callbacks" states; the failure is thrown again, the same value, once the library returns, before the result is examined, and the frame is dropped on every path.
- For a union declaring `_mixed_type_list`, `U_ALIGN` is the list's alignment, under a comment naming it the unit of `USequence.at`'s index, and `USequence` the Python module's lazy sequence in JavaScript's idiom: `length`, `bytes`, iteration and `at(index)`, the walk strict, `UnionError` thrown as the Python module raises it, with the same message, `index`, `offset` and `clause`, every tag, size and offset a literal of the definition's layout; a function's list parameter takes the sequence a callback of the same instance received, while that callback runs.
- The dead instance: an exception leaving a call into the module that the binding did not throw itself, a trap, the abort of a panic or a `RangeError` from the JavaScript stack, leaves the instance dead. A call in progress when its instance dies, one whose callback made the call that died, throws the dead-instance error once control returns to it, whatever its callback answered; and every later call of any of its objects throws an `Error` naming that first exception without reaching an export.
- Refused, each naming what it names: every 64-bit type in any position, a struct field, a boxed scalar's base type, a function's or callback type's parameter, an array's element or a buffer's count, as not implemented (`struct.stats.bytes: a 64-bit type, u64, is not implemented`); a struct field of opaque type, as not implemented; `--link=static`: `node: --link=static: the Node binding loads its module at run time and cannot link it statically`; a JavaScript reserved word as an argument, a function or a conversion; a struct field named `constructor`; an argument named like a global the module spells or a name it defines; a free function named like a parameter of `load` (`wasi`, `path`), whose declaration would shadow it; a name defined twice at module scope, in the library, or in a class (`constructor`, `handle`, `release` where a `_dtor` generates it, a method, a cached `out`), naming every definer; and a module-scope name a union's rendering defines that anything else defines, naming the union.

## Invocation

Two modes. Generation: `python3 -m langxyne <definition> --generated <dir> --project <name> [--library <name>] [--link=<mode>] [--outputs=<list>] [--check]`. The definition's file name, which every banner carries, must not contain a quote, a backslash or a control character (`the definition's file name must not contain '"', '\' or a control character`); a path separator, and so `*/`, cannot be in it. `--outputs` names the outputs to produce as a comma-separated list of tokens: `h` (the C header), `hpp` (the C++ wrapper), `lua` (the Lua module), `stub_cpp` (the C++ implementation stub), `rs` (the Rust binding), `abi_rs` (the Rust ABI relay), `stub_rs` (the Rust implementation stub), `go` (the Go binding), `py` (the Python module), `wasm_rs` (the wasm shim), `node` (the Node binding and its declarations); absent, every output but `wasm_rs` and `node`, which a WASI build of the library selects by name together. An unknown or repeated token is a usage error, exit status 2 with a message listing the valid tokens. No output implies another: the wrapper and the C++ stub include the header, and the Rust stub the relay, but selecting them neither adds `h` or `abi_rs` nor requires it. `--library` overrides `_general._bound_library`, is held to the same rule (`--library: 'libz.so' is a file name; name the library 'z'`) and must not be empty (`--library must name a library`), each objection to it reported beside the definition's loader objections, and a refused one draws no objection of a missing library; one of them must be present when `lua`, `rs`, `go`, `py` or `node` is selected, else the objection is `lua, rust, go, python, node: no library named; set _general._bound_library or --library` under the selected ones' labels. `--link` is how a consumer's build links the library, `shared` (the default) or `static`, any other value a usage error, exit status 2: an output that links at build time renders it (`rs`, `go`), one that loads at run time refuses `static` (`lua`, `py`, `node`), and every other output ignores it, as it ignores the library. A project wanting both modes generates in two runs with disjoint `--outputs`. Generating `rs`, `abi_rs` or `stub_rs` runs `rustfmt --edition 2024 --config-path /dev/null`, whose output the file is, so no `rustfmt.toml` beside, above or outside the definition, the user's own included, reaches it; without `rustfmt` on `PATH` generation exits 2 with `langxyne: rustfmt is required for the Rust outputs and was not found on PATH`, and a failing `rustfmt` exits 2 with its error, either way writing nothing. Generating `go` runs `gofmt`, whose output the file is, the same way, its messages naming `gofmt` and the Go output (`langxyne: gofmt is required for the Go output and was not found on PATH`). Exit status 0 on success with one line on stderr naming what was written; 2 on any definition error, with nothing written and each objection on its own line as `langxyne: <definition>: <what is wrong>`. A definition that breaks the format's own rules draws every objection the loader finds, in the document order of the items they concern, except that a structural failure leaving nothing to parse (a file that is not TOML, a missing or malformed `[_general]`, an unknown top-level table) draws its own objection alone; one that satisfies them draws every objection every selected output has, and none from an output not selected, all in the same run, each once, as `langxyne: <definition>: <outputs>: <what is wrong>`, where `<outputs>` names every selected output raising that same objection, comma-joined in the order `header`, `wrapper`, `lua`, `stub`, `rust`, `rust_abi`, `rust_stub`, `go`, `python`, `rust_wasm`, `node` (`header, wrapper, stub: struct.stats.int: 'int' is a C keyword`). A definition the format allows but the generator does not yet produce is refused the same way, the message saying `not implemented`. Every selected output is always written, and no other; staleness is the build's concern.

`--check` writes nothing. It generates exactly as above, every objection and tool error with it, exit status 2, then compares each selected output's text with its file under `--generated`, the file read as text, so line endings (`\n`, `\r\n` or `\r`) are aside; an output not selected is not compared. Exit status 0 when every one matches, with one line on stderr; exit status 1 when any differs or is missing, one line on stderr for each, `langxyne: <name>: <path> differs` or `langxyne: <name>: <path> is missing`, `<name>` being `_general._name` and `<path>` relative to the generated directory; exit status 2, with `langxyne: <the error>` on stderr, when a file there exists and cannot be read.

langxyne needs nothing but the Python 3.11 standard library. Where the `jsonschema` package imports, each mode that loads a definition first checks it against `api_def.schema.json`, and a definition the schema refuses draws the schema's objections in place of the loader's, each as `schema: <JSON pointer>: <message>` with the document line of the key at fault. `--no-schema` skips that check, as does the package's absence, and the loader's own objections stand.

Dependencies: `python3 -m langxyne gendeps [--outputs=<list>] [--link=<mode>] <definition>` prints make text to stdout for exactly one definition (one per project is the rule): `GENERATED :=` listing the selected outputs, `--outputs` as generation reads it, each followed by its companions (the Lua output's `lua/i64.lua` where the definition uses a 64-bit type in a value position, the Node binding's `node/<name>.d.mts`), as `$(GEN)/...` paths with `$(BASE)` for the project directory, and one grouped-target rule (`$(GENERATED) &: definition`, GNU make 4.3 or later) making them by running the generation mode with `--generated $(GEN) --project $(BASE)`, the same selection as `--outputs` and, where `--link=static` is given, that too. The including makefile defines `GEN`, `BASE` and `LANGXYNE`. It reads the definition's `_general._name`, which names the outputs, and the output paths come from the same code the generation mode writes to, so a build file never spells them. A definition the loader refuses draws its objections as generation reports them, exit status 2, with nothing on stdout. It runs no output's objections: a selection an output refuses, such as `--link=static` with `lua`, is reported when make runs the generation.

## Not generated

The wrapped API's header. It is the wrapped API's own, in whatever shape that API takes, and is never generated; the pins are the bridge. In this repository's tests it is a wrapped API's header beside a fixture definition. The API's implementation is hand-written too: the stub is a starting point handed over once, and the generator never touches the implementation. A Rust implementation is hand-written in its crate root, `lib.rs`, behind the regenerated relay.
